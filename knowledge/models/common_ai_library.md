**GitHub Repository:** [common_ai_library](https://github.com/Toku-Eyes/common_ai_library) — branch `main` (merged)
**Local Path:** `Models\common_ai_library`

> This is the shared base library, not an inference model. It is documented here because every model repo (`FROM ${BASE_IMAGE}`) depends on it directly.

## 1. Structure

Centralized repository that builds a single Docker base image (`common-ai-library`), replacing per-repo duplication of a `common/` folder across all 11 model repos.

The base image contains:
- All shared Python modules (expanded from 7 to 10, plus a native C++ extension package)
- All Python dependencies pre-installed
- Test tooling (`pytest`, `coverage`, `conftest.py`) pre-installed
- Shared scripts (`runtests.sh`, `sbom.sh`, `gpu-entrypoint.sh`) pre-installed

**Shared modules added (new, did not exist in old `common/`):**
- `inference_postprocesssing.py` — shared postprocessing logic
- `model_inference.py` — shared inference utilities (also hosts the `ThreadPoolExecutor` parallel-jury logic)
- `outbound_message_writing.py` — shared output formatting
- `opencv41_files/` — native C++ OpenCV 4.1.2 Gaussian blur extension

**Files removed from every model repo now that they inherit from this base image:**
- `common/` folder (7 files)
- `requirements.txt`
- `runtests.sh`, `sbom.sh`, `sbom_post.sh`
- `compile.py` (replaced per-model by `{model}_compile.py` using `tf_keras`)

### Docker Architecture

Before (per-model Dockerfile, ~60 lines):
```dockerfile
FROM nvcr.io/nvidia/tensorflow:22.08-tf2-py3 as base
RUN pip install --upgrade pip setuptools
RUN pip install -r requirements.txt
ADD common /root/common/
...
CMD [ "python3", "./main.py" ]
```

After (per-model Dockerfile, ~50 lines):
```dockerfile

FROM ${BASE_IMAGE} AS base
...
ENTRYPOINT ["/app/gpu-entrypoint.sh"]
CMD ["python3", "./main.py"]
```

Key changes: no `pip install` or `ADD common/` in model Dockerfiles, working directory moved from `/root/` to `/app/`, `ENTRYPOINT` added for hardware detection, `Dockerfile.standalone` added for independent builds, production stage unsets threading env vars so `gpu-entrypoint.sh` decides based on hardware.

## 2. Model-Wrapper API Contract (shared by every model)

Every model in the fleet is called through the same **model-wrapper** HTTP contract. Individual model files link back here instead of repeating the full schema.

### Request (input) — same for all models

`POST /api/extended/analyse` (model-wrapper) → fans out internally to each model's own `POST /api/inference` (port 80) with the same payload shape:

```json
{
  "FirstName": "sub1",
  "LastName": "sub1test",
  "Sex": "M",
  "camera": "OPTOS",
  "DOB": "1990/04/20",
  "DiabetesStatus": "No",
  "SmokingStatus": "No",
  "batchimages": [
    { "ImageName": "1.2.826.0....png", "Image64": "<base64-encoded PNG>" }
  ]
}
```

| Field | Type | Notes |
|-------|------|-------|
| `FirstName` / `LastName` | string | Placeholder/patient identifiers (auto-generated by the MCP client, not model input) |
| `Sex` | string | `M` or `F` |
| `camera` | string | `NW400`, `NW500`, `OPTOS`, or other — affects which preprocessing branch is used (e.g. `preprocess_image_nw500_v2` for NW500) |
| `DOB` | string | `YYYY/MM/DD` |
| `DiabetesStatus` / `SmokingStatus` | string | `Yes` / `No` — consumed by CVD/Bioage risk calculation |
| `batchimages` | array | 1+ objects with `ImageName` (string) and `Image64` (base64 PNG), tagged `left`/`right` via `ImagePosition` once decoded |

Full JSON Schema: [modelwrapper_request_schema.json](../templates/modelwrapper_request_schema.json); example: [modelwrapper_request_example.json](../templates/modelwrapper_request_example.json).

### Response (output) — aggregate envelope

The model-wrapper aggregates every model's individual JSON response under a `{model}_results` (or model-specific) key in one combined response. Full example: [modelwrapper_response_example.json](../templates/modelwrapper_response_example.json).

| Response key | Produced by | Shape |
|--------------|-------------|-------|
| `QC_Grade` | qc_model / qc2_model (+ optos_cropping_model via nested `qcoptoscropping`) | array of `{id, grade, position, centered, qcoptoscropping:{Croppable, Status, Error}}` |
| `r_result` | r_model | classification envelope (patient/left_eye/right_eye/images, per-jury probability rows) |
| `m_result` | m_model | classification envelope (patient/left_eye/right_eye/images, per-jury probability rows) |
| `rm_overall_results` | derived from r_model + m_model | `{result, risk, mModel:{...}, rModel:{...}}` — combined CLAiR traffic-light output |
| `dz_results` | dz_model | classification envelope, 3-class |
| `pa_results` | pa_model | classification envelope, 2-class |
| `ethnicity_results` | ethnicity_model | classification envelope, 2-class |
| `cvd_results` | cvd_model | patient-level regression object (no per-image breakdown) |
| `hba1c_results` | hba1c_model | regression + embedding envelope |
| `sbp_results` | sbp_model | regression + embedding envelope |
| `tchdl_results` | tchdl_model | regression + embedding envelope |

**Standard classification envelope** (`format_outbound_message()` in `common/outbound_message_writing.py`):
```json
{
  "patient": { "prediction": "<label>", "grade": "<optional human label>" },
  "left_eye": { "prediction": "<label>", "grade": "..." },
  "right_eye": { "prediction": "<label>", "grade": "..." },
  "images": [
    { "id": "...", "left_right": "left|right", "prediction": "<label>",
      "probability": [[<class probs>], ...], "embedding": null }
  ],
  "version": "0.0.0"
}
```
`probability` is a list of rows — one row per jury grader for that image (see §7.2 in [AI_INFRASTRUCTURE_ARCHITECTURE.md](../AI_INFRASTRUCTURE_ARCHITECTURE.md)); models whose example shows a single row are returning the jury-aggregated probability directly.

**Regression + embedding envelope** (`format_regression_embedding_outbound_message()`):
```json
{
  "patient": { "prediction": "<mean regression value as string>", "grade": null },
  "left_eye": { "prediction": "...", "grade": null },
  "right_eye": { "prediction": "...", "grade": null },
  "images": [
    { "id": "...", "left_right": "left|right", "prediction": "<value>",
      "probability": null, "embedding": [<mean embedding vector across jury>] }
  ],
  "version": "0.0.0"
}
```

## 3. Image Processing Steps

Owns the shared preprocessing/enhancement pipeline consumed by every model, defined in `common/image_preprocessing.py`:

**Standard pipeline** (`preprocess_image()`, used by most models):
1. Read image (from disk or memory, per `save_to_disk`)
2. Resolution check — reject if below 800px minimum
3. `crop_img()` — crop blank/black background, pad to square
4. Resolution check — reject if below 100px minimum (post-crop)
5. Resize to 1200×1200
6. Write/read cycle (disk or memory) — normalizes JPEG-compression artifacts
7. Resize to 800×800
8. `enhance_img_native()` — unsharp-mask enhancement using the native OpenCV 4.1.2 `GaussianBlur` extension (`alpha=4, beta=-4, gamma=128, scale_ratio=10`)
9. Save enhanced 800×800 image for model inference

**NW500 camera variant** (`preprocess_image_nw500_v2()`, used for the NW500 camera type):
1. Read → resolution check → crop → resize to 1200×1200
2. Apply salt-and-pepper noise (`apply_noise`)
3. Apply median filter (`apply_filter`)
4. Save filtered image

`DEBUG_SAVE_STEPS=true` saves intermediate images at every step for comparison/debugging.

Shared mechanics:
- `fetch_base64_json_images()` accepts a `save_to_disk` parameter, enabling the dual-mode pipeline:
  - **Disk mode** (`SAVE_IMAGES_TO_DISK=true`, default): writes intermediate images to disk
  - **Memory mode** (`SAVE_IMAGES_TO_DISK=false`): images stay as in-memory byte buffers through the whole pipeline, no disk writes between preprocessing and inference
- `get_enhance_function()` auto-loads the native OpenCV 4.1.2 Gaussian blur extension for models that require pixel-perfect legacy enhancement (QC, QC2) — see [qc_model.md](qc_model.md) and [qc2_model.md](qc2_model.md).
- All other OpenCV operations across all models use the modern 4.12.0 (`opencv-python-headless`) library.

### Native OpenCV 4.1.2 C++ Extension (hosted here, used by QC/QC2)
- `gaussian_blur_412_native.cpython-312-x86_64-linux-gnu.so` (Linux)
- `gaussian_blur_412_native.cp312-win_amd64.pyd` (Windows)
- Links against bundled `libopencv_core.so.4.1.2` and `libopencv_imgproc.so.4.1.2`
- Validated with 30+ pixel-equivalence test scripts in `important_files_for_upgrade_process/`

## 4. Model / Runtime Details

### Hardware Detection & Optimization Entrypoint (`gpu-entrypoint.sh`)
Used as the Docker `ENTRYPOINT` for all models. At container startup it:
- Detects CPU architecture (Intel XEON, AMD, generic) via `/proc/cpuinfo` and core count
- Detects GPU availability via `nvidia-smi` and TensorFlow
- **GPU mode:** minimal CPU threads (OMP/MKL/OpenBLAS = 2), TensorFlow GPU memory growth enabled
- **CPU mode:** all cores available, TF intra/inter-op threads auto-detected, oneDNN enabled
- Handles the `OMP_NUM_THREADS=0` edge case that crashes libgomp
- Respects user-set environment variable overrides

### Intel Xeon CPU Optimization
Target hardware: Azure `Standard_D16s_v6` (16 vCPU/64 GiB) and `Standard_D32s_v6` (32 vCPU/128 GiB), 5th-gen Intel Xeon Platinum 8573C (Emerald Rapids), AVX-512 + AVX-VNNI. K8s `nodeAffinity` pins AI pods to these SKUs.

- **Old approach (TF ≤2.15):** required `intel-extension-for-tensorflow` (ITEX) plugin for oneDNN graph fusions; last stable release targeted TF 2.15 only.
- **New approach (TF 2.20):** ITEX incompatible/unneeded — oneDNN is natively integrated. Single control: `TF_ENABLE_ONEDNN_OPTS=1` (default-enabled on modern Intel x86).
- oneDNN fuses Conv2D+Bias+ReLU and MatMul+Bias+BatchNorm into single primitives, reducing memory bandwidth pressure — measured throughput on `Standard_D16s_v6` matches the old ITEX+TF2.15 setup.
- Dedicated CPU-only build pipeline `build_push_cpudistro_vc1.sh` pushes images to `tokuairegistry.azurecr.io/cpudistro` for all 12 models.

### Keras 3 Compatibility Layer
`tf-keras==2.20.0` added as a compatibility shim since TF 2.20 ships Keras 3 (breaking API changes):
```python
try:
    import tf_keras
    from tf_keras.models import load_model
    from tf_keras.preprocessing.image import ImageDataGenerator
except ImportError:
    from tensorflow.keras.models import load_model
    from tensorflow.keras.preprocessing.image import ImageDataGenerator
```
Each model has its own `{model}_compile.py` and `{model}_model_launching.py` using this layer.

### Parallel Inference for Multi-Grader Models (shared implementation)
`common/model_inference.py` implements opt-in parallel jury inference via `ThreadPoolExecutor`, used by R, M, CVD, and HbA1c models:

| Environment Variable | Default | Description |
|----------------------|---------|--------------|
| `PARALLEL_INFERENCE` | `false` | Set to `true` to enable parallel jury inference |
| `PARALLEL_INFERENCE_THREADS` | `min(jury size, cpu_count())` | Max concurrent threads |

Each grader thread owns an independent `ImageDataGenerator`; after inference, generators/DataFrames are deleted and `gc.collect()` runs. ~20% inference-time reduction observed; higher memory use is the trade-off; sequential mode remains the default fallback with identical behavior.

### Inference Enhancements (shared across all models)
- Probability outputs: `pred.tolist(), pred_prob.tolist()` for confidence scoring (previously class labels only)
- Optional `enable_timing` param logs `[TIMING]` markers per model/step
- `printEnvVariables()` and `printOpenCVExtensionStatus()` called at startup for diagnostics

## 5. Deployment & Infrastructure (Kubernetes)

All 12 model services (+ OptosCropping) are deployed as independent workloads on a shared Azure Kubernetes Service (AKS) cluster, fronted by the model-wrapper.

### Cluster topology
- **Namespace-per-environment:** separate `staging` and `production` namespaces; each model repo deploys its own `Deployment` + `Service` pair into both.
- **Node pools:**
  - **GPU node pool** — NVIDIA GPU-backed nodes (CUDA 12.6.0/cuDNN 9.x) for models run in GPU mode; `gpu-entrypoint.sh` detects `nvidia-smi` availability and sets TensorFlow GPU memory growth.
  - **CPU node pool** — Intel Xeon Platinum 8573C (Emerald Rapids) SKUs `Standard_D16s_v6` (16 vCPU/64 GiB) and `Standard_D32s_v6` (32 vCPU/128 GiB), pinned via Kubernetes nodeAffinity/nodeSelector for the CPU-only image distribution (`cpudistro`) built by `build_push_cpudistro_vc1.sh`.
- **Container images:** pulled from Azure Container Registry — `tokueyesproduction.azurecr.io/models/{model}:buildid-N` (GPU images) and `tokuairegistry.azurecr.io/cpudistro/{model}` (CPU-only images). The shared `common-ai-library` base image is versioned by `buildid` and referenced via the `BASE_IMAGE` build ARG in every model's Dockerfile.
- **Service/Ingress:** each model exposes its Flask/Waitress inference API on container port 80 (`POST /api/inference`) via a ClusterIP Service; the model-wrapper service is the single entry point that fans requests out to each model Service by internal DNS name (`{model}-model.{namespace}.svc.cluster.local`) and aggregates responses into the combined envelope (§2).
- **Health/readiness:** `gpu-entrypoint.sh` performs hardware detection before the app starts; container readinessProbe/livenessProbe hit the model's inference endpoint to gate traffic until TensorFlow/Keras model weights are loaded.
- **Scaling:** GPU-mode pods typically run as fixed-replica deployments (GPU node pool capacity-bound); CPU-mode pods can use a HorizontalPodAutoscaler keyed on CPU utilization, since oneDNN-optimized inference on Xeon SKUs scales roughly linearly with vCPU count.

### CI/CD deployment pipeline
Each model repo's GitHub Actions workflows call shared reusable workflows from `Toku-Eyes/central-workflow`:
- `pr.yaml` — build + unit test on PR
- `staging-build-and-push.yaml` → `staging-deploy-to-k8.yaml` — builds the image, pushes to ACR, applies the Deployment/Service manifests (or Helm chart) to the `staging` namespace
- `production-build-and-push.yaml` — same, gated to `production` namespace on release/tag
- `fast-deploy-to-staging.yaml` — expedited path for rapid iteration, skipping the full build matrix

Rolling updates use the standard Kubernetes RollingUpdate strategy so the model-wrapper never routes to a pod before its readiness probe passes (i.e., before model weights are loaded into memory).

## 7. Security & Vulnerability Remediation

Before: ~150 CVEs per container (outdated Python packages, NVIDIA base image, Ubuntu 20.04 OS packages).
After: 0 vulnerabilities across all 12 repos, verified via Dependency-Track SBOM scans (CycloneDX 1.6, 4 Mar 2026), risk score 0.

Key actions: upgraded direct deps (Keras 3.13.2, Flask 3.1.3, Werkzeug ≥3.1.4, cryptography ≥44.0.0, PyJWT ≥2.10.0, urllib3 ≥2.6.3, zipp ≥3.21.0); removed and re-pinned Ubuntu 24.04 system Python packages (`cryptography`, `PyJWT`, `oauthlib`, `zipp`, `httplib2`); replaced base image with `nvidia/cuda:12.6.0-cudnn-runtime-ubuntu24.04`.

### SBOM generation (CycloneDX) & Dependency-Track scanning process

Every model repo's CI pipeline runs the shared `sbom.sh` script (inherited from this base image) as part of each build:
1. **Generate SBOM** — `sbom.sh` runs a CycloneDX generator against the fully-built container image, producing a CycloneDX 1.6 JSON SBOM listing every direct and transitive dependency (Python packages, native shared-library extensions, OS packages) with name, version, and package-URL identifiers.
2. **Upload to Dependency-Track** — the generated SBOM is POSTed to the organization's self-hosted Dependency-Track instance via its REST API, associated with that repo's project entry (versioned per build, e.g. `qc_model v13`).
3. **Vulnerability matching** — Dependency-Track continuously matches every component in the SBOM against the National Vulnerability Database (NVD), OSS Index, and GitHub Advisories, recalculating a per-project risk score and vulnerability count whenever either the SBOM changes or a new CVE is published.
4. **Gate/report** — each model's knowledge file Security section reports that project's latest Dependency-Track scan snapshot (SBOM version, vulnerability count, risk score, scan date). A risk score of 0 and 0 vulnerabilities means no known CVEs currently match any component in that build.
5. **Re-scan cadence** — Dependency-Track re-evaluates existing SBOMs against newly-published CVEs automatically (no rebuild required), so a previously clean project can surface new findings without a code change; a fresh SBOM is generated and re-uploaded on every CI build regardless.

**This repo's scan result:** SBOM v5, 0 vulnerabilities, risk score 0, last scan 3 Mar 2026.
